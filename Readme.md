# Служба доставки беспилотниками — вариант 38 (уровень 7–8)

Учебный симулятор на **C11 для Linux**. Модель доставки сохранена из предыдущей версии; добавлены три программы с **настоящими процессами ОС** и POSIX IPC. Не требуется C++, сторонние библиотеки или фреймворки.

## Что моделируется

На клетчатой карте есть склад, препятствия, беспилотники, заказы и зарядные станции. Диспетчер выбирает подходящий аппарат с учётом груза, энергии и дедлайна. Путь строится BFS. Каждый такт аппарат перемещается на одну клетку. В плохую погоду полёт приостанавливается; станции продолжают зарядку. В конце выводится статистика.

## Три реализации по уровням ТЗ

| Исполняемый файл | Запуск процессов | Синхронизация / передача данных |
| --- | --- | --- |
| `fly_fork_unnamed` | родитель создаёт 4 дочерних через `fork()` | неименованные POSIX-семафоры (`sem_init`) и `mmap(MAP_SHARED)` |
| `fly_fork_named` | родитель создаёт 4 дочерних через `fork()` | именованные семафоры (`sem_open`) и `shm_open` |
| `fly_external_shm` | контроллер и 4 работника запускаются отдельно | именованные семафоры (`sem_open`) и POSIX shared memory (`shm_open`, `mmap`) |

В архиве сохранён `fly_simulator` — **старая pthread-версия только для сравнения и тестирования**, не для сдачи как процессный вариант.

Один работник занимается всеми объектами своей роли: `orders`, `dispatcher`, `drones` или `stations`. Процессы асинхронно ожидают сигнала своего этапа на семафоре. Чтобы результат был воспроизводимым, контроллер активирует роли строго по очереди.

## Сборка и запуск

Сборка в Linux/WSL (GCC и make):

```bash
make
make test
```

Запуск первых двух схем:

```bash
./fly_fork_unnamed --scenario scenarios/demo.txt --delay 50
./fly_fork_named --scenario scenarios/demo.txt --delay 50
```

Запуск независимых процессов (обёртка создаёт лог):

```bash
bash scripts/run_external.sh --scenario scenarios/demo.txt --delay 50
```

Для ручного запуска открыть пять терминалов из корня проекта. У всех один `--instance` и один сценарий:

```bash
# Терминал 1
./fly_external_shm --instance demo --scenario scenarios/demo.txt

# Терминалы 2–5 (каждая команда отдельно)
./fly_process_worker --transport shm --role orders --instance demo --scenario scenarios/demo.txt
./fly_process_worker --transport shm --role dispatcher --instance demo --scenario scenarios/demo.txt
./fly_process_worker --transport shm --role drones --instance demo --scenario scenarios/demo.txt
./fly_process_worker --transport shm --role stations --instance demo --scenario scenarios/demo.txt
```

Контроллер создаёт пространство общих данных, четыре работника к нему подключаются, информируют о готовности и обрабатывают фазы. При остановке контроллера по `Ctrl+C` работники завершают работу.

Другие полезные параметры: `--quiet`, `--delay MS`, `--max-time N`, `--weather-interval N`, `--instance ID`, `--cleanup --instance ID`. `--cleanup` использовать только для **остановленного** экземпляра.

## Как устроен IPC

1. Контроллер загружает сценарий и кладёт в shared memory текущее состояние модели **без указателей**.
2. Через семафор `start[role]` разрешает ровно одному работнику выполнять фазу.
3. Работник читает состояние, восстанавливает локальные указатели, выполняет `simulation_step_role()` и записывает изменённое состояние назад.
4. Работник вызывает `sem_post(done[role])`; контроллер ждёт его через `sem_wait` и переходит к следующей фазе.
5. Семафор `lock` защищает доступ к общему состоянию. Все ресурсы удаляются при штатном завершении и `SIGINT`/`SIGTERM`.

`process_snapshot.c` нужен, потому что адреса указателей в двух **независимых** процессах не обязаны совпадать. Передаются плоские поля моделей; маршруты и связи станции с беспилотниками восстанавливаются локально.

## Структура

```text
inc/                       заголовочные файлы
src/map.c                  сетка и поиск BFS
src/plane.c                параметры аппаратов и перемещение
src/order.c                заказы
src/station.c              зарядка
src/dispatcher.c           назначение заказов
src/weather.c              смена погоды
src/scenario.c             загрузка сценария
src/simulation.c           общий шаг моделирования и статистика
src/main.c                 старая версия на pthread (эталон)
src/process_controller.c   родитель / контроллер
src/process_worker.c       отдельно запускаемый работник
src/process_ipc.c          mmap + sem_init / sem_open / shm_open
src/process_snapshot.c     упаковка состояния без указателей
scenarios/                 четыре сценария
scripts/run_external.sh    удобный запуск независимых процессов
tests/test_sim.c           10 модульных проверок
tests/test_process.sh      15 проверок процессов
report.tex                 редактируемый отчёт
report.pdf                 готовый отчёт
```

## Входной сценарий

Текстовые файлы в `scenarios/`. Пример:

```text
size 5 5
warehouse 0 0
block 2 1
station 1 4 4 2 5
drone 1 0 0 5 60 60 2
order 1 4 0 3 0 20
weather_interval 0
max_time 30
```

Синтаксис и проверки параметров унаследованы от исходного проекта. Координаты — `(строка, столбец)`, индексация от нуля; `#` — комментарий.

## Проверки

`make test` запускает **10 модульных + 15 интеграционных проверок**: 3 режима на 4 сценариях, дополнительно 3 теста корректного прерывания по `SIGINT`. Результаты процессных версий сравниваются с прежней версией на pthread.

| Сценарий | Такты | Заказов | Доставлено | Отказов | Шагов |
| --- | ---: | ---: | ---: | ---: | ---: |
| `small.txt` | 8 | 1 | 1 | 0 | 8 |
| `deadline.txt` | 17 | 3 | 1 | 2 | 8 |
| `demo.txt` | 150 | 6 | 4 | 2 | 163 |
| `batch.txt` | 12 | 61 | 1 | 60 | 11 |

**Ограничения:** один процесс на **семейство**, а не на каждый отдельный объект. Фазы синхронизированы последовательно, что соответствует учебной задаче по IPC, но не обеспечивает параллельное ускорение. В окончательном отчёте требуется заполнить ФИО и группу.
